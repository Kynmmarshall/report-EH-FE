1 Introduction & Scenario Recap

SecureTech Solutions Ltd. is a 120-employee software and digital services company that reported unau-
thorized login attempts, weak/reused passwords, suspicious web server activity, possible customer data
exposure, unpatched systems, and no centralized monitoring. Our team was authorized, in writing, to sim-
ulate both a Red Team (offensive) and a Blue Team (defensive) inside a contained laboratory only — never
against production systems.
    This document covers Task 1 (Laboratory Design & Documentation): the physical and virtual network
we built, every VM from first install to a verified static IP, the real problems we hit while bringing the network
up, and the pfSense access-control configuration that enforces the lab’s security boundary. The companion
Post-Configuration Execution Guide picks up from here and walks Tasks 2–13.
  Authorized Scope
  All offensive and defensive activity described in both documents is confined to the isolated lab segment
  192.168.50.0/24. Nothing here is ever pointed at a host outside this range.

4 Design-Level Strategy

  Red Team — Network-Level Intent
  Rayan and Bruno treat 192.168.50.0/24 as the target range. Their plan is to (1) sweep the whole sub-
  net from Bruno’s Kali box (PC4) to build an asset map, (2) fingerprint the server/web/target stack hosted
  on Rayan’s PC3, (3) look for a foothold on the Metasploitable/DVWA targets first since they are inten-
  tionally weak, then (4) pivot from that foothold toward Fahdil’s workstation (PC2) to simulate lateral
  movement toward an “employee” asset, all while assuming pfSense (PC1) and the OpenVAS/Suricata

  accordingly.

  Blue Team — Network-Level Intent

  point all inter-host traffic must cross, with a default-deny LAN ruleset and only the narrow exceptions
  defined in Section 10; (2) run Suricata in the Kali VM on PC1 in promiscuous IDS mode against the

5 PC1 — Marshall: pfSense Gateway + Suricata IDS (Blue Team)

PC1 is the centralized firewall, router and traffic-inspection point for the entire lab. It runs two guest VMs
under one VirtualBox hypervisor: a pfSense VM (LAN gateway/firewall) and a Kali Linux VM dedicated to
running Suricata as a passive IDS sensor.

5.1 Install VirtualBox and create the pfSense VM
   1. Install Oracle VirtualBox (and the matching Extension Pack) on the PC1 host machine.
   2. Download the current pfSense CE installer ISO from the official pfSense site.
   3. In VirtualBox: New → Name pfSense-GW, Type BSD, Version FreeBSD (64-bit).
   4. Allocate 2048 MB RAM, 2 vCPUs, and a 20 GB dynamically allocated VDI disk (pfSense itself is light;
      this leaves headroom for packages and logs).
   5. Settings → Storage: attach the pfSense ISO to the virtual optical drive.
   6. Settings → System → Processor: enable PAE/NX.

5.2 Network adapters for pfSense
pfSense needs two NICs: one for the uplink (WAN) and one for the lab LAN.
   1. Settings → Network → Adapter 1 (WAN): Attached to NAT. This lets pfSense reach the internet (pack-
      age/plugin downloads, patches) without exposing the lab.
   2. Settings → Network → Adapter 2 (LAN): Attached to Bridged Adapter, Name = the physical host’s
      active Wi-Fi adapter. Expand Advanced and set Promiscuous Mode: Allow All.
  Host-Only Adapter attempt failed
  Our first attempt used a Host-Only Adapter for the LAN leg on every PC, assuming it would behave like
  a normal lab switch. It did not work: a VirtualBox Host-Only network is a virtual switch that exists only
  inside one physical hypervisor — it never leaves that physical machine’s NIC. Because our five students
  are on five separate physical PCs connected only over Wi-Fi, each PC’s VMs ended up on their own
  isolated Host-Only segment with no path to the other four PCs: pings between VMs on different physical
  machines timed out, DHCP requests to pfSense never arrived, and pfSense’s LAN interface only ever
  saw its own host’s loopback traffic. Fix: switch every LAN-side adapter (pfSense and all four clients)
  to Bridged Adapter bound to each machine’s physical Wi-Fi NIC, with Promiscuous Mode: Allow All.
  Bridging makes every VM appear as its own device directly on the physical Wi-Fi segment, so all five
  physical PCs’ VMs can finally see one another.


5.3 Initial pfSense console staging
   1. Power on the pfSense VM and let the installer finish; reboot into the console menu.
   2. At the console menu, choose 2) Set interface IP address.
   3. Select the LAN interface, assign the static address 192.168.50.1.
   4. Enter the subnet bitmask: 24.
   5. When prompted, enable the DHCP server on LAN (optional — we assign static addresses to every
      client instead, see Sections 6–9).
  Expected Outcome
  The console menu reports the LAN interface as 192.168.50.1/24, UP. From any host already bridged
  onto the LAN segment:

5.5 Suricata-in-Kali IDS VM (second VM on PC1)
A second guest VM on the same PC1 hypervisor runs Kali Linux purely as a Suricata sensor — it is never used
to attack, only to listen.
   1. VirtualBox New → Name PC1-Suricata-IDS, Type Linux, Version Debian (64-bit). Allocate
      4096 MB RAM, 2 vCPUs, 40 GB disk.
   2. Attach the Kali Linux installer ISO and complete a standard installation.
   3. Settings → Network → Adapter 1: Bridged Adapter on the same physical Wi-Fi NIC, Promiscuous
      Mode: Allow All (required so this VM can passively see LAN traffic that is not addressed to it).
   4. Assign it a static management address, 192.168.50.200/24, gateway 192.168.50.1.
  Suricata installation & ruleset update
  # update package lists and install Suricata
  sudo apt update && sudo apt install -y suricata jq

  # confirm the interface that should see LAN traffic
  ip -brief addr show

  # point Suricata at the lab subnet (HOME_NET line is indented under
  # vars: address-groups: in suricata.yaml, so the pattern must allow
  # leading whitespace or the substitution silently matches nothing)
  sudo sed -i 's/^\( *HOME_NET:\).*/\1 "[192.168.50.0\/24]"/' \
      /etc/suricata/suricata.yaml

  # confirm the substitution actually took effect
  grep "HOME_NET:" /etc/suricata/suricata.yaml

  # pull the current ET-open ruleset (a fresh install ships almost no rules)
  sudo suricata-update

  Why suricata-update is required
  A freshly installed Suricata only ships a handful of example rules. Without running suricata-update
  at least once, most ET-open signatures referenced later in this guide and in Task 11 of the Execution
  Guide (scan, exploit, and web-attack categories) simply do not exist yet, so nothing would alert regard-
  less of how the sensor is wired up.

  Custom local rule: detect a port-scan threshold
  Suricata does not flag a plain SYN scan out of the box the way a scanner-detection engine would — this
  has to be added as a local rule using a threshold clause, which counts matching packets per source
  over a time window.
  sudo nano /etc/suricata/rules/local.rules

  Contents of local.rules
  alert tcp any any -> $HOME_NET any (msg:"LOCAL Potential TCP Port Scan"; \
    flags:S; threshold:type threshold, track by_src, count 20, seconds 10; \
    classtype:attempted-recon; sid:1000001; rev:1;)

  Confirm local.rules is loaded, then start Suricata
  # the default rule-files list may not reference local.rules yet --
  # add it right after the "rule-files:" line only if it's missing
  grep -qxF ' - local.rules' /etc/suricata/suricata.yaml || \
    sudo sed -i '/rule-files:/a\ - local.rules' /etc/suricata/suricata.yaml

  # validate the configuration and new rule before going live
  sudo suricata -T -c /etc/suricata/suricata.yaml -v

  # enable and start Suricata in IDS (listen-only) mode on the bridged interface
  sudo systemctl enable --now suricata

  # tail live alerts as JSON, filtered to readable fields
  sudo tail -f /var/log/suricata/eve.json | jq 'select(.event_type=="alert")'

  Expected Outcome
  systemctl status suricata reports active (running). The eve.json tail stays idle until
  traffic matching a signature crosses the bridged interface; once Red Team traffic starts in the compan-
  ion Execution Guide, alert JSON objects appear here in real time — this is the evidence base for Task 11
  (Blue Team Investigation).

  Why a Kali VM for Suricata instead of pfSense’s own package
  pfSense ships a Suricata package that can run inline on its own interfaces, but we deliberately run Suri-
  cata on a separate Kali VM in promiscuous, out-of-band mode instead. This keeps the firewall VM (PC1’s
  pfSense guest) lean and dedicated purely to routing/filtering, while the IDS sensor can be rebuilt, tuned,
  or have its ruleset updated without any risk of taking down the lab’s only gateway.

6 PC2 — Fahdil: Windows Workstation (Blue Team)

PC2 represents the “employee computer” asset named in the exam brief. Fahdil, as Blue Team, is responsible
for keeping it patched and auditing its credential policy (feeds Task 8 and Task 12 in the Execution Guide).
   1. VirtualBox New → Name PC2-Workstation, Type Microsoft Windows, Version Windows 10
      (64-bit). Allocate 4096 MB RAM, 2 vCPUs, 60 GB disk.
   2. Attach a Windows 10 installer ISO and complete a standard installation with a local employee-style
      account (no Microsoft account, to mirror a realistic corporate workstation).
   3. Install the VirtualBox Guest Additions (Devices → Insert Guest Additions CD image) for better dis-
      play/clipboard integration.
   4. Settings → Network → Adapter 1: Bridged Adapter on the host’s physical Wi-Fi NIC, Promiscuous
      Mode: Allow All.
   5. Inside Windows, open Control Panel → Network and Sharing Center → Change adapter settings →
      IPv4 Properties and set a static configuration: IP 192.168.50.10, Mask 255.255.255.0, Gateway
      192.168.50.1, DNS 192.168.50.1 (forwarded by pfSense).
  Verify Wi-Fi MAC and connectivity (PowerShell / Command Prompt)
  :: confirm the physical Wi-Fi adapter MAC (avoids duplicate-MAC conflicts)
  getmac /v

  :: confirm the static address took effect
  ipconfig /all

  :: confirm the pfSense gateway answers
  ping -n 4 192.168.50.1

  Expected Outcome
  ipconfig /all shows IPv4 Address 192.168.50.10, Subnet Mask 255.255.255.0, Default Gate-
  way 192.168.50.1. The ping to the gateway returns 4 replies.

  Difficulty: duplicate MAC warning during early bridging tests
  While still experimenting with Host-Only networking (see Section 5), we briefly cloned a VM instead
  of reinstalling, which duplicated a MAC address across two guests. Once both were bridged onto the
  same physical Wi-Fi segment this caused ARP cache thrashing and intermittent dropped pings. Fix: in
  VirtualBox, Settings → Network → Advanced → Generate new MAC address on the cloned adapter
  before powering it on, and never clone an already-bridged VM without doing this.

9 PC5 — Amina: OpenVAS / Greenbone Vulnerability Scanner (Blue Team)

PC5 runs the automated vulnerability assessment platform used in Task 5. This is also where the lab hit its
most serious build problem.
   1. VirtualBox New → Name PC5-OpenVAS, Type Linux, Version Debian (64-bit). Allocate 8192
      MB RAM, 4 vCPUs.
   2. Allocate a 80 GB (dynamically allocated) virtual disk — see the difficulty note below for why this num-
      ber matters.
   3. Install Kali Linux (ships a one-command GVM/OpenVAS setup) or a minimal Debian with the Green-
      bone Community Edition packages.
   4. Settings → Network → Adapter 1: Bridged Adapter, Promiscuous Mode Allow All. Assign a static
      address 192.168.50.250/24, gateway 192.168.50.1.
  Install and initialize GVM/OpenVAS
  # install the Greenbone Vulnerability Management suite
  sudo apt update && sudo apt install -y gvm

  # one-time setup: builds the DB, syncs NVT/SCAP/CERT feeds, creates admin user
  sudo gvm-setup

  # verify the install is healthy before first use
  sudo gvm-check-setup

  Difficulty: gvm-setup / feed sync repeatedly failed
  Our first VM for PC5 was built with the same 20–40 GB disk we used for the other hosts. gvm-setup and
  gvm-check-setup failed repeatedly with feed synchronization errors and PostgreSQL write failures.
  The root cause was insufficient virtual disk space, not insufficient video memory: the combined NVT,
  SCAP and CERT feed data plus the PostgreSQL vulnerability database that GVM builds on first run require
  well over 40 GB once fully synced, and our undersized disk filled up mid-sync, corrupting the partial feed
  state on every retry.
  Fix:
     1. Power off the VM. In VirtualBox, use File → Virtual Media Manager to increase the VDI’s logical
        size to 80 GB (or clone to a larger disk).
     2. Boot into the guest and grow the filesystem to use the new space.

  # identify the root partition/volume
  lsblk

  # grow the root partition to fill the new disk size (distro-dependent)
  sudo growpart /dev/sda 1
  sudo resize2fs /dev/sda1

  # re-run the health check until it reports no errors
