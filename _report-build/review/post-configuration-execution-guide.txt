2 Task 2 — Reconnaissance & Asset Discovery (4 marks)

Runs on: PC4 Bruno (Kali, PC4).    Goal: discover every live host on 192.168.50.0/24 and build the asset
inventory table.
  Red Team Strategy
  Bruno’s opening move is a wide, low-noise sweep first (host discovery only, no port scan) to map who
  exists before touching anything — this limits the footprint Blue Team’s IDS sees in the first pass. Only
  after the asset map is built does he escalate to per-host fingerprinting (-A), expecting pfSense/Suricata
  logging to pick this up from here on.

  Host discovery sweep
  # find every live IP on the subnet without touching any ports yet
  nmap -sn 192.168.50.0/24

  OS/service fingerprint pass per discovered host
  nmap -A 192.168.50.1   -oN scan_pfsense.txt      # gateway/firewall
  nmap -A 192.168.50.10 -oN scan_workstation.txt   # Fahdil's Windows 10 workstation
  nmap -A 192.168.50.20 -oN scan_server.txt        # Rayan's server host
  nmap -A 192.168.50.30 -oN scan_dvwa.txt          # nested DVWA/Juice Shop
  nmap -A 192.168.50.40 -oN scan_metasploitable.txt
  nmap -A 192.168.50.200 -oN scan_suricata.txt     # Marshall's IDS sensor (PC1)
  nmap -A 192.168.50.250 -oN scan_openvas.txt      # Amina's OpenVAS scanner (PC5)

  Expected Outcome
  The -sn sweep reports 7 hosts up. Each -A scan returns open ports, service versions, and a guessed OS
  — record IP, MAC vendor, guessed OS, and open ports per host into the asset inventory table (feeds Task
  13’s Asset Inventory deliverable). This output tells Bruno which hosts are worth enumerating further
  in Task 3, and tells Marshall/Amina (Blue Team) what a baseline recon sweep looks like in their logs for
  comparison in Task 11.

  Video/Screenshot
  VIDEO — start recording before the nmap -sn sweep, narrate expected vs. actual host count, stop after
  the last -A scan. SCREENSHOT — the -sn output, and one -A output per host, overlay visible.

3 Task 3 — Service Enumeration (4 marks)

Runs on: PC4 Bruno (Kali, PC4). Goal: identify service versions, protocols, and web technologies on each
target to justify which entry points to attack.
  Red Team Strategy
  With the asset map from Task 2 in hand, Bruno narrows focus to the hosts that matter for exploita-
  tion — Rayan’s server/target stack — and goes deep: every port, every version, every script-assisted
  enumeration. The DVWA/web stack gets its own fingerprinting pass since Task 7 depends on knowing
  exactly what is running there.

  Full deep port/version scan against server and web targets
  nmap -sV -sC -p- 192.168.50.20 192.168.50.30 192.168.50.40 -oN full_scan.txt

  Fingerprint the web app stack
  whatweb 192.168.50.30
  curl -I http://192.168.50.30

  Targeted NSE scripts against Metasploitable services
  nmap --script=smb-enum-shares -p445 192.168.50.40
  nmap --script=ftp-anon        -p21 192.168.50.40

  Expected Outcome
  -sV -sC -p- returns the full version/service table for all three hosts (expect FTP, SSH, Telnet, SMTP,
  HTTP, SMB and MySQL-class services on the Metasploitable target). whatweb/curl return the web
  server banner and DVWA’s login page headers. The SMB/FTP NSE scripts report whether shares are
  browsable and whether anonymous FTP is enabled — both are Task 5/6 candidate findings if so.

  Video/Screenshot
  VIDEO — record the full -sV -sC -p- scan (narrate what each open port could mean while it runs)
  plus the whatweb/curl step. SCREENSHOT — version/service table per target, and the header output
  for the web app.

8 Task 8 — Credential Security Assessment (4 marks)

Runs on: PC4 Bruno (attack, Kali PC4) against Fahdil’s and Rayan’s hosts; PC2 Fahdil (policy review, PC2).
Goal: audit password policy weaknesses and demonstrate a password attack.
  Red Team Strategy
  Bruno treats weak/default/reused credentials as the lowest-effort path to access, consistent with the
  scenario’s own incident list (“employees using weak or reused passwords”). Brute-forcing DVWA’s login
  and SSH on Metasploitable both target accounts with no lockout policy — exactly the gap Blue Team is
  asked to close.

   1. DVWA’s brute-force page requires an authenticated session — log in to DVWA in a browser first (any
      valid account, security level low), open DevTools → Application/Storage → Cookies, and copy the
      PHPSESSID value. Without this cookie, every Hydra attempt just hits the login redirect and “fails”
      regardless of the password tried.
  Brute-force the DVWA login form
  hydra -l admin -P /usr/share/wordlists/rockyou.txt 192.168.50.30 \
    http-post-form "/dvwa/vulnerabilities/brute/:username=^USER^&password=^PASS^\
  &Login=Login:Login failed:H=Cookie: security=low; PHPSESSID=<paste_session_id_here>"

  Brute-force SSH on the Metasploitable target
  hydra -l msfadmin -P /usr/share/wordlists/rockyou.txt ssh://192.168.50.40

  Crack a captured password hash
  john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
  hashcat -m 0 hash.txt /usr/share/wordlists/rockyou.txt

  Expected Outcome
  hydra reports a recovered valid credential pair once it matches a weak entry in the wordlist (fast against
  rockyou.txt because these are intentionally weak lab accounts). john/hashcat report the cracked
  plaintext for any captured hash. Each successful crack is direct evidence for the policy weaknesses Fahdil
  documents next.

  Blue Team Strategy
  PC2 Fahdil reviews the workstation’s local account policy (or the DVWA/service login policy) and records
  concrete weaknesses observed from the attack above: no lockout threshold, no complexity rule, default
  credentials still active. Recommendations: enforce lockout after N failed attempts, minimum complex-
  ity, and MFA where the platform supports it — feeds directly into Task 12’s hardening plan.

  Video/Screenshot
  VIDEO — record the hydra/john run from launch to a successful cracked credential, with the policy
  weakness explained in narration. SCREENSHOT — the password policy weakness (config/settings page)
  and the successful brute-force/crack output.

  Enumerate the internal network view from the compromised host
  arp -a
  netstat -antp
  cat /etc/hosts

  Open a SOCKS pivot through the compromised host

  # through the Metasploitable host's own network view

  # line reads "socks5 127.0.0.1 1080", then route a scan through the pivot

  Alternative: forward one specific service through the pivot

  # then browse http://127.0.0.1:8080 on Bruno's own machine

  vantage point. If pfSense’s ACL (see Lab Network Configuration, rule 5) is working as designed, the

 PC2 Fahdil .  Goal: reconstruct Red Team’s entire campaign from its first packet in Task 2 through Task 10,

  Blue Team Strategy
  Marshall’s Suricata sensor has been running in promiscuous IDS mode on the LAN backbone since before

11.1 Live alert monitoring — fast.log (primary, always works)
Suricata writes every alert to two places: the simple text log fast.log (one line per alert, no JSON parsing
needed, never fails) and the richer JSON log eve.json used for the structured queries later in this section.
Start here — it has zero dependencies and is the fastest way to confirm the sensor is alive and alerting at all.
  Watch alerts live, then filter what you already captured
  # live tail while Red Team's commands run in another task
  sudo tail -f /var/log/suricata/fast.log

  # afterward: every alert sourced from (or aimed at) Bruno's Kali box
  # (note: IP is followed by :port in this log, not a bare space, so match
  # on the IP substring itself rather than assuming "IP -> " is adjacent)
  grep "192.168.50.100:" /var/log/suricata/fast.log

  # afterward: only port-scan-category alerts, any source
  grep -i "scan" /var/log/suricata/fast.log

  # count alerts per source IP, busiest first (quick triage across a whole capture)
  grep -oP '\{(TCP|UDP|ICMP)\}\s+\K[0-9.]+(?=:)' /var/log/suricata/fast.log | \
    sort | uniq -c | sort -rn

  Expected Outcome
  Each line is self-contained and human-readable, e.g.                   [**] [1:2024364:5] ET SCAN
  Possible Nmap User-Agent Observed [**] … {TCP} 192.168.50.100:36252 ->
  192.168.50.1:80 — source IP, destination IP/port, and the signature name are all visible without
  any JSON tooling. The ranked count command immediately tells Marshall which host is generating the
  most alerts right now, which is the IP to act on first in the block step below.

  Why two log formats
  fast.log is intentionally simple and will never fail to parse — use it for live triage and for anything
  this guide’s jq/eve.json commands don’t cover. eve.json carries structured fields (dest_port,
  full alert metadata) that enable the precise per-task queries below, but because Suricata is actively
  appending to it, a slurp-mode JSON parse can occasionally land on a line being written mid-flush — the
  commands below are written to tolerate that.

Before filtering for anything specific, get the whole picture in time order so later, narrower queries can be
justified by what this first pass shows.

  Full Suricata alert timeline, oldest first (resilient to a bad line)
  # stage 1: parse each line independently; fromjson? silently drops any
  # line that isn't valid JSON yet (e.g. one being written mid-flush),
  # instead of aborting the whole pipeline the way "jq -s" alone would
  # stage 2: now that every object is known-good, sort and shape the output
  jq -R 'fromjson? // empty' /var/log/suricata/eve.json | \
    jq -s 'map(select(.event_type=="alert")) | sort_by(.timestamp) | .[] |
      {timestamp, src_ip, dest_ip, dest_port, signature: .alert.signature}'

  Expected Outcome
  This returns one JSON object per alert in chronological order. Expect the very first entries to be port-
  scan/recon-category hits with src_ip = Bruno’s 192.168.50.100 — that is Task 2’s nmap -sn sweep.
  Keep this output; Sections 11.3–11.6 below re-query the same file narrowed to one task at a time so
  each finding can be cited by task number in the report.

  Difficulty: jq -s alone crashed with “Invalid numeric literal”
  Running jq -s 'sort_by(.timestamp) | ...' directly against eve.json while Suricata was
  still actively writing to it failed with jq: parse error: Invalid numeric literal at line
  48, column 501 — one line was a partial JSON object (caught mid-write), and slurp mode (-s) re-
  quires every line to parse before it will process any of them. Fix: the two-stage fromjson? // empty
  pipeline above parses each line independently and silently discards the one bad line instead of aborting
  the entire query — use this pattern for any live-tailed JSON log, not just this one.


11.3 Task 2/3 — Reconnaissance and enumeration, then block the source

  Isolate scan-detection alerts from Bruno’s host
  jq -R 'fromjson? // empty' /var/log/suricata/eve.json | \
    jq 'select(.event_type=="alert" and .src_ip=="192.168.50.100" and
      (.alert.signature | test("[Ss]can")))'

  Expected Outcome
  Expect a burst of scan-category alerts starting at the timestamp of Bruno’s nmap -sn sweep, with a sec-
  ond, larger burst later matching the -p- full-port scan in Task 3 (same signature family, far higher alert
  count in a shorter window because every port is probed, not just a host-discovery ping). The destina-
  tion IPs across both bursts cover the whole 192.168.50.0/24 range for the first sweep, narrowing to
  .20/.30/.40 for the Task 3 pass — that narrowing is itself evidence Red Team moved from discovery
  to targeting.

  Detect → Block, on pfSense
  Once a source IP is confirmed malicious from the alert output above, Marshall blocks it at the firewall
  immediately — this is the action half of Task 11/12, not just observation.

  Block the offending source at pfSense (GUI, then CLI equivalent)
  # GUI: Firewall > Aliases > add/edit "Blocked_Attackers" (type: Host(s)),
  # add the offending IP as a member, Save + Apply. Then Firewall > Rules >
