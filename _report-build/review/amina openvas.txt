1 Executive Summary

Task 5 of the SecureTech Solutions security assessment required an automated vulnerability scan
of the lab target set (192.168.50.20, .30 and .40) using OpenVAS / Greenbone Vulnerability
Management (GVM), followed by manual cross-checking and CVSS-based triage of at least five
findings. This report documents that the task could not be completed as specified.
    Although the OpenVAS service and its web interface were operational, the Greenbone data
feeds that GVM depends on had not finished synchronizing. The SCAP data feed remained in an
“Update in progress” state and the GVMD Data feed — the component that supplies the default
Port Lists and scan configurations — had not been imported. As a direct result, the scanner
refused to create a scan target, reporting that the default Port List was unavailable, and no scan
task could therefore be created or launched. No vulnerability results were produced.
    The synchronization was attempted five times. On the fifth and final attempt observed, the
SCAP data store grew from approximately 1 001 MB to 1.1 GB over roughly one hour before
stalling without completing. Substantially increasing the VM’s resources (disk, memory and pro-
cessors, detailed in §9) did not change the outcome. The failure is an environmental / configura-
tion blocker, not a finding about the target network. This report records the evidence, establishes
the root cause, assesses the impact on the wider engagement, and sets out the remediation re-
quired to bring the feeds to a “Current” state so that Task 5 can be re-run.

7 Root-Cause Analysis

GVM cannot scan until several locally-held data feeds are synchronized and imported: the
NVT feed (the vulnerability tests), the SCAP data feed (CVE / CPE data loaded into the gvmd
database), the CERT data feed, and the GVMD Data feed, which provides the default Port Lists,
the “Full and Fast” scan config and the report formats.
   Primary cause — incomplete feed synchronization. The SCAP feed was still importing
(“Update in progress”, Figure 1) and the GVMD Data feed had not loaded, shown directly by
gvmd’s inability to read its feed.xml (Figure 3). Because the GVMD Data feed is exactly what
supplies the default Port List, its absence produced the precise error seen on save (Figure 6). The
scanner was installed correctly, but it had nothing to build a target or a scan config from.
    Contributing factors:

• Feed volume: the SCAP / CVE dataset is large (over 1 GB here), and the Greenbone Commu-
  nity Feed is rate-limited, so a full sync can take hours or stall on a constrained connection.
• Repeated restarts: five separate attempts can each interrupt and re-lock the import, so the
  sync never gets an uninterrupted window to finish.
• Resources were increased but it still failed: an earlier installation error on this host was
  cleared by raising the base memory from 2000 MB to 4000 MB, and for Task 5 the VM was
  pushed further (disk 30 GB to 80 GB, memory 8000 MB, 2 processors). The synchronization
  still did not complete — indicating the remaining bottleneck is the feed download / import
  itself (data volume and the rate-limited community feed), not local CPU, RAM or disk.
• Partial-sync signature: NVT reaching “Current” while SCAP and GVMD Data lagged is con-
  sistent with the heavier CVE import simply not having finished.

   Important distinction: this is an environmental / tooling blocker on the scanner, not a vul-
nerability or misconfiguration of the target network. It says nothing about the security posture of
192.168.50.20 / .30 / .40.

• Resolved an installation error hit while setting up OpenVAS / GVM by increasing the VM’s

• Verified feed state in Administration → Feed Status (SCAP in progress, NVT current).
• Monitored   the    SCAP    data   directory                 growth       with   watch sudo du -sh

• Inspected gvmd output and identified the missing GVMD Data / CERT feed.xml warnings.
• Re-attempted target creation several times — the same default-Port-List error recurred each

• Re-ran the full synchronization up to a fifth attempt; the fifth run (1.1 GB) continued for about
  an hour without completing.
• Increased the VM’s resources for the scan attempts — expanded the virtual disk from 30 GB
  to 80 GB, raised the base memory to 8000 MB, and allocated 2 processors — but the synchro-
  nization and scan were still unsuccessful.


10 Recommendations and Remediation

To bring the scanner to a working state and re-run Task 5:

 1. Run one uninterrupted sync to completion. Avoid repeated restarts. Use sudo
    greenbone-feed-sync, which pulls the NVT, SCAP, CERT and GVMD Data feeds; allow sev-
    eral hours as the community feed is large and rate-limited.
 2. Confirm all feeds read “Current” in Administration → Feed Status — not just NVT — before
    creating any target.
 3. Verify the GVMD Data feed actually loaded: Configuration → Port Lists should list the
    defaults (e.g. “All IANA assigned TCP”) and Configuration → Scan Configs should show “Full
    and Fast”. Their absence is what caused the error.
 4. If a feed is stuck, sync components individually to isolate it: sudo greenbone-feed-sync
    --type scap and sudo greenbone-feed-sync --type gvmd-data.
 5. After syncing, rebuild and restart: sudo gvmd --rebuild, then sudo gvm-stop && sudo
    gvm-start (or restart the gvmd and ospd-openvas services).
 6. Run sudo gvm-check-setup to confirm that no feed component is empty or missing.
 7. Resources are already ample — focus on time and connectivity: with the disk at 80 GB,

11 Conclusion

The OpenVAS vulnerability assessment for Task 5 could not be completed because the Greenbone
data feeds — specifically the SCAP data feed and the GVMD Data feed that supplies the default
Port Lists and scan configurations — never finished synchronizing, despite five attempts, a final
run of roughly one hour at 1.1 GB, and substantial increases to the VM’s disk (30 GB to 80 GB),
memory (to 8000 MB) and processors (to 2). The scanner itself was installed and reachable; the
blocker is environmental — the feed download and import, not local resources. With the feeds
brought fully to “Current” and the service rebuilt and restarted as set out in §10, the target can
be created and the Full and Fast scan executed, allowing Task 5 to be delivered as specified. Until
then, the manual cross-checks remain available to produce interim findings.
